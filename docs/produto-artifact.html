01

O que estará no MVP

O roadmap oficial do produto define um MVP1 com 7 módulos e DNA integrado em todos eles. Essa continua sendo a visão final: o corte abaixo é um primeiro degrau, dimensionado pro que o estado real do backend permite entregar de verdade num mês, não uma substituição da ambição original.

Entra neste corte
AutenticaçãoCadastro, login, logout, sessão persistente
PerfilVer e editar dados básicos, preferências de categoria
LugaresBase real, com categoria, localização e horário
Mapa + ExplorarLugares reais, ordenados pelo motor de recomendação (DNA, contexto, pesos)
SalvosMarcar "quero ir" / "já fui", sem calendário ainda
Fica como melhoria
Feed socialPosts, fotos, curtidas, comentários: zero backend hoje
ComunidadesCriação, participação, moderação: zero backend hoje
Agenda avançadaCalendário, eventos, lembretes
Pesquisa globalNão iniciada
IntegraçõesFotos reais, clima real, mapa de verdade, geolocalização
DNA no servidorO motor já existe e funciona, rodar no servidor é pra quando um segundo cliente precisar dele

O critério por trás da divisão: dá pra demonstrar "o que vale a pena viver, agora" sem esse módulo? Mapa, Explorar e Salvos com recomendação de verdade já contam essa história. Feed e Comunidades contam uma história diferente (de rede social), que vale construir em seguida, não ao mesmo tempo.

04

Pontos estratégicos a validar

Direção estratégica: confirmada, não precisa mudar

Vale reforçar o que já está decidido antes de construir mais features: VISION.md é explícito (descoberta é o eixo primário, comunidade sustenta a confiança na recomendação, não é ponto de partida).

Comunidades depois, não antes: já é a decisão tomada

Entender o usuário de verdade antes de construir pertencimento. É exatamente a sequência que a seção 01 já propõe: Comunidades fica como melhoria, fora do corte deste mês.

Geolocalização com raio definido

O roadmap já lista geolocalização na Fase 11, de forma genérica. Vale ser específico desde já: busca por lugares precisa de um raio configurável ("experiências a até 5 km"), não só "usar a localização do usuário".

Validar aderência por território e categoria antes de escalar

Delimitar uma combinação específica (uma região da cidade + uma categoria, como gastronomia) pra confirmar que a recomendação funciona antes de abrir pra tudo. Cabe no passo 5 da seção anterior.

Monetização ainda não está no papel

O que mais falta hoje: nenhum documento discute como o produto gera receita. Pensar a jornada monetizada com B2B (lugares pagando por visibilidade) e B2C (assinatura) desde já. Antes de validar qualquer frente B2B, confirmar que é um ativo de valor de verdade.

Lacuna registrada, não decisão
Não precisamos fazer tudo agora, mas precisamos ter tudo mapeado

Já é como este documento está estruturado: um corte pequeno pra este mês, o resto mapeado no roadmap, não esquecido.

05

Parte técnica

Só pra quem vai construir, não precisa entrar na conversa de produto.

Stack

  • Frontend: React 18 + Vite 6 + Tailwind 4, em web/
  • API: NestJS + Prisma + PostgreSQL (PostGIS), em api/
  • Repo único e privado, sem ferramenta de monorepo

Como rodar

  • npm install + npm run dev dentro de cada pasta
  • Banco: Postgres gerenciado no Supabase (região São Paulo), connection string em api/.env
  • Ver README.md na raiz do repositório
  • O banco pausa sozinho por inatividade (free tier). Reativa abrindo o projeto no painel do Supabase (~1 min); nunca rodar prisma migrate dev nesse estado
  • Sem RESEND_API_KEY no api/.env, o código de verificação só é logado no servidor (modo dev). Pra enviar de verdade: conta grátis em resend.com

Testes

  • API: Jest, npm test em api/
  • Convenção: todo módulo novo de backend entra com teste antes de ser considerado pronto
  • Frontend ainda sem suíte: decisão pra quando parar de ser só mock

Decisões que não se reabrem sem motivo novo

  • Autenticação é nossa, nunca de provedor externo
  • Toda rota nasce protegida; público é exceção explícita
  • Erro sempre vira AppException
  • Motor de recomendação com implementação única, em web/src/engine/, até o backend precisar dele de verdade
  • seedTags no Place é ponte temporária (EMENDA-004), não o desenho final do DNA
  • Avatar é preset de emoji, não upload. preferredCategories é preferência declarada, não entra no DNA do usuário ainda
  • SavedPlace.placeId é texto solto, sem FK pro Place (mesmo raciocínio do seedTags/EMENDA-004)
  • Verificação de e-mail é só no cadastro, não em todo login. SHA-256 no código (não Argon2): quem barra força bruta é o limite de tentativas, não o custo do hash
